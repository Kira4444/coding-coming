# Coding Agent 项目介绍

## 一、产品定位

**Coding Agent** 是一套可部署在团队服务器上的 Web 版智能编程助手。

用户指定一个代码库、用自然语言描述需求，agent 自主完成「读代码 → 改代码 → 跑验证 → 提交改动」的完整闭环。全程在浏览器里可视化呈现每一步思考与操作，关键动作需人工确认。

| 项 | 内容 |
|---|---|
| **目标用户** | 3–20 人的研发小团队 |
| **交付形态** | 开源（Apache-2.0），docker-compose 一键部署 |
| **模型底座** | 对接任意 OpenAI 兼容接口（小米 MiMo、DeepSeek、智谱 GLM、自部署 vLLM 均可） |

一句话概括——**把"改代码"这件事从人写变成人审**。

---

## 二、解决的问题

### 现状痛点

| 痛点 | 后果 |
|---|---|
| 重复性改代码工作（加字段、补测试、改命名）占据大量时间 | 研发精力被低价值工作稀释 |
| 代码库知识集中在少数人脑中 | 新人上手慢，改动易踩坑 |
| 传统补全工具只帮"写一行"，不帮"完成一件事" | 效率提升有限 |
| 已有的 AI 编程工具多为个人桌面端 | 团队难共享配置、难追溯审计、难管控风险 |

### 我们的思路

**不做一个"更聪明的补全"，而是做一个"能进沙箱干活的同事"**——它有明确的能力边界、可审计的行为记录、以及需要人拍板的决策点。

## 三、核心能力

### 1. 智能代码修改

Agent 采用**工具检索 + 精确替换**的技术路线：

- 用 `glob` 找文件、`grep` 定位代码、`read_file` 精读片段——不靠向量索引，靠真实检索
- 用 **search/replace 精确替换**改代码，`old_text` 必须唯一匹配
- 改完自动跑测试/构建验证，失败会读错误信息自我修正
- 每完成一个阶段自动 `git commit`，提交说明规范

**编辑格式的选择是关键**：整文件重写容易漏改，diff 格式对中等能力模型不可靠。search/replace 块是 Cursor / Claude Code 验证过的最优解，对中等模型最稳。替换失败时整体拒绝写盘，不应用部分编辑——避免文件进入模型没预期的状态。

### 2. 项目级 Agent 配置

每个项目可以独立配置 agent 的工作方式：

| 配置项 | 说明 |
|---|---|
| **项目专属指令** | 技术栈、代码约定、目录结构、构建方式。追加到通用系统提示之后 |
| **可用工具开关** | 按项目禁用某些能力（如禁止 shell） |
| **默认审批策略** | `全自动` / `写操作确认` / `始终确认` |
| **执行预算** | 最大轮次、Token 上限，按项目收紧 |
| **忽略路径** | agent 不碰的目录（对齐 gitignore 语义） |
| **沙箱镜像** | 项目可用自带工具链的定制镜像 |
| **模型覆盖** | 按项目指定不同模型 |

这让同一个 agent 在不同项目上表现不同——**前端项目知道要用 pnpm，Java 项目知道必须跑 mvn test**。

### 3. MCP 工具扩展

支持挂载任意 **MCP（Model Context Protocol）** 服务器，为 agent 增加外部工具能力。

- **真 MCP 客户端**，自研 stdio JSON-RPC 实现（握手、工具发现、调用）
- **工具带命名空间** `mcp__{服务器}__{工具名}`，不与内置工具冲突
- 项目级独立配置，互不干扰
- 一键「测试连接」，真起进程握手验证
- 外部工具能力不可预知，调用**一律要求人工确认**

### 4. Skills 技能库

一组可复用的指令包，agent 按需加载：

- 系统提示只放**索引**（名字 + 一句话描述）
- agent 需要时用 `load_skill` 拉取完整正文
- **按需加载而非全量注入**——上下文预算花得值

效果：`前端开发规范`、`数据库迁移流程`、`提交信息约定` 这类团队知识可以沉淀成技能，跨任务复用。

### 5. 会话与工作区隔离

```
项目 Project ──┬── 工作区 Workspace（代码的一份独立副本）
               └── 会话 Session（一次对话，绑定工作区与专属分支）
```

- **一会话一工作区**——隔离干净，会话之间互不干扰
- **一会话一分支**——改动不会污染主干
- 会话记录永久保存，工作区 7 天后回收磁盘
- 支持 git URL 导入与本地路径导入

### 6. 可追溯的交付

| 能力 | 说明 |
|---|---|
| **实时思考过程** | 推理模型的思考内容流式展示，可折叠回看 |
| **工具调用卡片** | 每次工具调用的命令、输出、耗时，可展开 |
| **Diff 视图** | 文件级增删统计 + hunk 高亮渲染 |
| **Patch 下载** | 一键导出标准 patch 文件 |
| **命令审计日志** | 谁、何时、让 agent 跑了什么，全程可追溯 |
| **Token 用量统计** | 按会话统计消耗 |

**MVP 不做 git push**——合并由用户自己把关。这是刻意的边界。

## 四、产品形态

### 页面清单

| 页面 | 路径 | 用途 |
|---|---|---|
| 登录 | `/login` | 内置账号体系 |
| 项目列表 | `/projects` | 项目卡片管理 |
| 项目详情 | `/projects/:id` | 代码来源、Agent 配置、MCP、Skills、会话列表 |
| 会话列表 | `/sessions` | 全部会话，按项目筛选 |
| 对话 | `/sessions/:id` | 对话流 + 工具卡片 + 审批 + Diff 视图 |
| 设置 | `/settings` | 账号改密、模型 provider、沙箱配置 |

### 典型工作流

```
1. 建项目 ──── 填代码库路径 / git 地址
2. 配 Agent ── 写项目约定、勾选可用工具、调审批策略
3. （可选）挂 MCP 工具、写 Skill
4. 开会话 ──── 系统自动准备代码工作区 + 建专属分支
5. 描述任务 ── "给这个函数补上单元测试"
6. 观察执行 ── 思考过程流式显示，工具调用逐步展开
7. 审批关键动作 ── shell 写操作弹窗确认
8. 验收交付 ── 看 diff、下 patch
```

## 五、架构设计

### 整体架构

```
┌─────────────────────────────────────────────────────┐
│  frontend（Vue3 + Vite）                            │
│    对话流 · 工具卡片 · 审批交互 · Diff 视图 · 配置面板 │
└───────────────────────┬─────────────────────────────┘
                        │ HTTP + SSE
┌───────────────────────▼─────────────────────────────┐
│  backend（Spring Boot 3 + WebFlux）                 │
│                                                     │
│  web/       HTTP API、SSE、DTO、错误映射             │
│  agent/     agent loop、工具集、上下文预算、审批      │
│  model/     OpenAI 兼容 provider 抽象                │
│  sandbox/   执行环境驱动（local / docker）           │
│  mcp/       MCP stdio 客户端 + 工具适配              │
│  skill/     技能按需加载                             │
│  storage/   MyBatis-Plus → MySQL                    │
└──────┬──────────────────────────────┬───────────────┘
       │                              │
       ▼                              ▼
┌──────────────┐            ┌──────────────────────┐
│    MySQL     │            │  沙箱容器（一会话一个）│
│ 会话 · 历史  │            │  bind mount 工作区    │
│ 审计 · 用量  │            │  资源限额 · 网络策略   │
└──────────────┘            └──────────────────────┘
```

### 关键流程：一次任务执行

```
用户输入
  ↓
构造系统提示（通用规则 + 项目专属指令 + 技能索引）
  ↓
┌─────────────────────────────────────┐
│  发给模型 ←────────────────┐        │
│    ↓                      │        │
│  流式响应：思考 + 文本 + 工具调用   │
│    ↓                      │        │
│  工具调用 → 审批闸门 → 执行        │
│    ↓                      │        │
│  结果回填到对话历史 ───────┘        │
│  （直到模型不再要工具）             │
└─────────────────────────────────────┘
  ↓
提交改动 · 生成 diff · 推送 SSE 事件
```

### 分层解耦的意图

三条明确的边界，让各层可独立替换：

| 边界 | 替换成本 |
|---|---|
| `SandboxDriver` 接口 | local 换 Docker，agent 层零改动 |
| `LlmProvider` 接口 | MiMo 换 DeepSeek，只改配置 |
| `Tool` 接口 | 新增工具不用改 agent loop |

## 六、关键技术决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 代码理解 | 纯工具检索（grep/glob） | 向量索引复杂度高、收益不确定；工具检索已被验证可靠 |
| 编辑格式 | search/replace 块 | 对中等模型最稳，失败不写盘 |
| Agent loop | 自研阻塞实现 | 工具执行同步、审批要等人，响应式会让控制流散落 |
| 上下文管理 | 硬截断 + 预算控制 | 不做自动压缩；一次 `npm test` 的输出能吃掉几万 token |
| 沙箱 | 一会话一容器 | 隔离干净；不跨会话复用避免状态残留 |
| MCP 工具命名 | `mcp__server__tool` | 多服务器同名工具不冲突 |
| 技能加载 | 索引 + 按需拉取 | 全量注入会撑爆上下文 |
| 推理过程 | 只存不传 | MiMo 等模型禁止 reasoning 回填 |
| 数据库 | MySQL（开发用 H2） | 生产成熟稳定，开发免装库 |

## 七、安全模型

Coding agent 能跑 shell，权限模型是产品的一部分。

### 沙箱隔离

| 驱动 | 隔离性 | 适用 |
|---|---|---|
| `local` | 无隔离，命令以服务进程身份运行 | **仅限开发** |
| `docker` | 一会话一容器、资源限额、非 root 用户 | 生产必须 |

### 分级审批

| 动作 | 默认策略 |
|---|---|
| 文件读 | 自动 |
| 文件写 | 自动（可开提示） |
| shell 只读命令 | 自动 |
| shell 写 / 危险命令 | **需人工确认** |
| MCP 外部工具 | **需人工确认** |

策略三档可配：`auto` / `ask-on-write` / `always-ask`。

### 其他防线

- **网络策略**：沙箱默认允许公网出网（否则装不了依赖）、默认禁内网
- **命令审计日志**：全程可追溯
- **输出截断**：避免超长输出淹没上下文
- **密钥保护**：API key 加密入库、界面掩码、`.env` 不入库
- **路径越界防护**：工具只能读写工作区内

### 已知风险

**提示注入**无法根除——仓库里的代码、注释、README 都可能含恶意指令。现有防线是审批闸门 + 审计日志 + 系统提示的硬性禁令。

**Docker socket 挂载**：生产部署时 backend 需挂宿主机 Docker socket 以开沙箱容器，这等于给了它 root 级权限。缓解措施（rootless Docker、专用 Docker 实例、独立主机）已写入部署文档。

## 八、部署形态

### 一键部署

```bash
cp .env.example .env    # 填入模型 API key
docker compose up -d
```

包含三个服务：**MySQL 8.4** · **后端（Spring Boot）** · **前端（Nginx + Vue）**。

### 模型接入

任何 OpenAI 兼容接口都能接，配置三元组即可：

```yaml
coding-agent.model.providers.mimo:
  base-url: https://api.xiaomimimo.com/v1
  api-key: ${MIMO_API_KEY}
  model: mimo-v2.6-flash
```

已实测：小米 MiMo。配置就绪：DeepSeek、智谱 GLM、自部署 vLLM/SGLang。
